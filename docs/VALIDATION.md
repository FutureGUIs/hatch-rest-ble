# Validation status and device test plan

## Version 0.2.0 status

**227 unit tests passed** on 2026-10-15 for 0.2.0, covering the protocol, transport, output controls, and native program parsing and transactions. This combined result includes the 71 new program codec cases for classic fields, encodings, validation bounds, native flag changes, deletion, local clock values, and firmware-gated lock commands, plus six enable-baseline cases added in the final revision. The final Ruff lint and formatting rerun passed for all **35 Python files**, including HA tests; linting those tests does not execute them. Historical results below describe earlier releases.

Comparison with the 0.1.5 release found no removed files. The existing light, media player, protocol, entity base, constants, and approved branding files are byte-identical to 0.1.5. Shared setup/transport code and the added native-program path still require the unrun HA and hardware checks below.

Release packaging checks passed: Python syntax and JSON validity, matching English strings/translations, version 0.2.0, required program and branding files, ZIP integrity, and exclusion of APK/DEX files, research, and generated caches. The archive contains 47 files with no removed files compared with 0.1.5.

The full Home Assistant suite and all physical-device checks remain unrun locally. No real program table has been read, no program has been written to a Rest, and no HA instance or Bluetooth device has been controlled during development. Application acknowledgements, partial-write behavior, concurrent app edits, clock accuracy, program retention, and firmware execution with HA/proxy offline still require the checks below. Mocked I/O and app inspection do not establish those hardware guarantees.

## Physical checks

1. Install the component, restart HA, close the phone app, and verify discovery of a first-generation Rest. Confirm that another Hatch model does not get added. Add a second Rest if available and verify separate devices and entity IDs.
2. Read power, RGB, brightness, sound, and volume; compare them with the app. Use media-player Off/On for whole-device power, including native preset restoration and physical-button changes. Verify power actions send only `SI00`/`SI01` when needed, with no extra color, sound, or volume commands.
3. Set one color and brightness together. Turn the light off while audio is playing, then turn it on. Verify Color loop and return to a static color.
4. Select each source. Set volume to zero, halfway, and maximum. For hardware version beginning `2`, verify the minimum maps to raw8 and maximum to raw255. Minimum volume on that revision may still be audible; use Pause to silence playback.
5. Pause twice and play while powered on. Verify Pause leaves the lamp active and Play resumes the last observed nonzero sound. Restart HA with sound None and verify Play's Pink noise fallback. Test None and zero brightness while off without waking the device.
6. Issue several light and media actions at once. Verify no overlapping connections and that readback matches the final device state. Adjust `COMMAND_SETTLE_SECONDS` only if firmware responds before applying a command.
7. Unplug the Rest or move it out of range. Verify entities become unavailable and actions report failure. Restore it and confirm recovery on a later poll.
8. Test through a local adapter and an active proxy separately. Change the available Bluetooth route and verify the next session follows HA's selected route.
9. Reload and remove/re-add the integration, then stop HA. Verify connections are released and discovery works again. Open the app between polls and verify it can connect after the integration disconnects.
10. Leave two plugged-in Rests with light and sound off for several hours through the affected ESPHome proxy. Confirm continued updates, app access between polls, and addition of the second Rest. Capture integration and proxy debug logs if an invalid-handle error persists. Check whether the backend reports that on-device cache clearing is unavailable with the installed ESPHome firmware.
11. Compare the delay between a command, the physical device change, the confirmed HA state change, and service completion. Use debug timings to distinguish connection/lock waits from disconnect time. Change the per-device polling option between 5 and 60 seconds, confirm the entry reloads, and check that app/button updates follow the new interval plus connection time. Verify both Rests remain usable with the faster setting.
12. From whole-device off, turn on the HA light and confirm the requested color and brightness. Repeat with media Play and source selection. Check how the Rest's firmware restores the other output; it may resume sound during light wake or resume the lamp during sound wake. Verify light wake sends only `SI01` then requested `SC`, and sound wake sends only `SI01` then selected `SN`, without suppressing the other output or reapplying volume. While already powered on, verify changes preserve the counterpart's settings. Light Off must darken only the lamp; Pause/None must silence only audio. Media Off must turn off both outputs.
13. Upgrade an existing entry with its old Power switch registered. After successful setup, verify only that obsolete switch is removed, Light/Sound entity IDs remain stable, and local Hatch branding is present. Update old switch automations to media-player On/Off. With only the lamp active and source None, verify media state is Idle and its power toggle turns the whole device off. Verify Off, Idle, and Playing states against shared power and sound selection, including a nonzero sound at zero volume.

## Native-program checks

1. Record the complete existing program list and settings in the Hatch app before any write. Load **Configure → Manage programs** and compare names, slots, enabled states, days, times, duration, color, brightness, sound, volume, and available toddler-lock settings. Verify the read leaves all device programs unchanged, including disabled programs and names containing Unicode.
2. Use an unused slot first. Choose **Add a new program**, create a short disabled test program, compare every saved field in the app, then edit it and verify HA/app readback. Confirm other slots and current lamp/audio remain unchanged by the program write. Check full-table load with all ten occupied slots and the absence of Add a new program when full.
3. Enable and disable the test program through its Configuration switch and editor. Verify only the native enabled flag changes; the switch does not start/stop current lamp/audio or claim a current-running state. Schedule a future start and check how edits or disabling during a run affect the next start. Keep this separate from the media player's whole-device power actions.
4. Rename the program and confirm its slot-based switch identity remains. Delete it and confirm only its slot entity is pruned, preserving Light/Sound and other program entries. Repeat app-side create/edit/delete followed by the **Refresh programs** button, **Refresh programs from the Rest** in the editor, and the 15-minute background refresh.
5. Open a program in HA, change it through the app after HA disconnects, then submit the older HA form. Verify save, delete, and enable/disable confirmation report a conflict and do not overwrite newer values. Repeat with an empty slot becoming occupied, a slot deleted/reused by a different program, and a stale switch request whose enabled value already matches the device. Verify switch conflicts report an action error and the table becomes unavailable until refreshed. Refresh and reopen the program before trying again.
6. On the expendable slot, exercise command errors, missing or fragmented acknowledgements, disconnects, cancellation, and failed post-commit readback. Verify failed/uncertain writes are reported, no mutation sequence is replayed automatically, the connection is released, and a fresh read reveals the actual slot state before another attempt. Check buffers/timeouts with malformed or excessive reply data using a simulator rather than risking existing programs.
7. Compare the last-read `GT` device time with the app and a local clock. Verify HA sends no clock-set command. If correction is needed, use the app's Device Time → Sync Time, then refresh. Test local timezone differences, overnight durations, repeated/skipped DST hours, and overlapping programs; compare behavior with [Hatch's classic Rest guidance](https://help.hatch.co/hc/en-us/articles/115003020554-Daylight-Savings-and-Your-Hatch-Devices). A displayed start-plus-duration summary is not proof of a fixed wall-clock end.
8. Schedule an expendable program shortly in the future, then shut down HA and disconnect its proxy while leaving the Rest powered. Verify native start and completion without HA/app access, then restore HA and read the program again. Separately test unplug/replug retention and clock recovery. These checks establish device execution and persistence rather than inferring them solely from command structure.
9. Exercise nonblank 1–16-byte ASCII names, reserved reply words, Unicode reads/toggle/delete, minute duration limits, unchanged existing duration seconds, selected weekdays, brightness, all built-in sounds, and both volume scales. Verify toddler lock is available only with a known supported firmware version and that unsupported firmware causes no lock write. Check that unrelated opaque settings survive edits.
10. Run table polling and live controls together for several hours through the affected ESPHome proxy with two Rests. Verify one per-device connection at a time, live reads/actions after table transactions, recovery after source/proxy changes, and cleanup on reload, unload, and HA stop. Compare command latency during initial and manual table refreshes. Confirm HA does not create persistent program options or a second scheduler, and existing Light/Sound IDs and branding remain stable.

This release implements native program management alongside light, sound, volume, and power. Timers, automatic clock/DST writes, firmware updates, raw command entry, calendar integration, fades, multistep routines, monthly/exception scheduling, and additional device models remain outside its implemented scope.
